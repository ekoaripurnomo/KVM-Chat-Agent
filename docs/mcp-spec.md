# MCP Integration Specification (TASK-001)

Findings from inspecting `steveydevey/kvm-mcp` (default branch `main`) — the
actual server source, not just the README.

## Transport

- JSON-RPC 2.0 over **stdio**. The server reads one JSON request per line from
  stdin (`sys.stdin.readline`) and writes one JSON response per line to stdout.
- Supported methods:
  - `initialize` → `{ protocolVersion, serverInfo: { name: "kvm-control" } }`
  - `tools/call` with `params = { name, arguments }`
- There is **no `tools/list` method** in the current server implementation.
  Tool discovery therefore cannot be dynamic against this server; the client
  ships a static, source-derived tool catalog and exposes it via
  `GET /api/mcp/tools`. This is documented here per spec Rule 2 (do not assume
  tool names/args solely from the README).

## Tools (source-derived schemas)

### `create_vm`
`arguments`:
| field | type | required | notes |
|-------|------|----------|-------|
| `name` | string | yes | rejected if it contains ``!@#$%^&*()+={}[]\|\\:;"'<>?/`` |
| `memory` | int (MB) | yes | 256 ≤ memory ≤ 1048576 |
| `vcpus` | int | yes | 1 ≤ vcpus ≤ 128 |
| `disk_size` | int (GB) | no (default 20) | 1 ≤ disk_size ≤ 10000 |
| `network` | string | no (default `brforvms`) | |
| `master_image` | string | **yes** | must exist on the KVM host; used as qcow2 backing file |
| `ignition` | object | **yes** | Fedora CoreOS ignition config |
| `os_variant` | string | no (default `fedora-coreos-stable`) | |

Returns `{ "status": "success" | "error", "message": string }`.
Disk path is hard-coded by the server to `/vm/{name}.qcow2` and fails if it
already exists (natural VM-name collision guard).

### `list_vms`
`arguments`: `{ "use_cache": bool = true }`.
Returns a list of `{ name, id, state, autostart, persistent }`.

### `start_vm`
`arguments`: `{ "vm_name": string }`. Returns `{ success, message | error }`.

### `stop_vm`
`arguments`: `{ "vm_name": string, "force": bool = false }`.
Returns `{ success, message | error }`.

### `reboot_vm`
`arguments`: `{ "vm_name": string }`. Returns `{ success, message | error }`.

## Config defaults (server `config.json`)

`disk_path=/vm`, `default_iso=ubuntu-24.04.2-live-server-amd64.iso`,
`default_master_image=fedora-coreos-41-qemu.x86_64.qcow2`, `default_memory=2048`,
`default_vcpus=2`, `default_disk_size=20`, `default_os_variant=generic`,
`default_network=brforvms`. Overridable via `VM_DEFAULT_*` env vars on the
server side.

## Discrepancy with the app spec (and how we handle it)

The app spec describes an **ISO-based Ubuntu** create flow. The real `create_vm`
tool is **Fedora-CoreOS/ignition** oriented: it requires a host-side
`master_image` and an `ignition` dict, and ignores ISO.

Decision (spec Rule 10 & 11 — do not invent parameters, prefer explicit errors):

- The canonical intent stays OS-agnostic (name/os/vcpu/mem/disk/network).
- The VM Service maps the intent onto the real tool arguments:
  - `name → name`, `memory_mb → memory`, `vcpus → vcpus`, `disk_gb → disk_size`,
    `network.bridge → network`, `os.variant → os_variant`.
  - `master_image` comes from **application configuration**
    (`MCP_DEFAULT_MASTER_IMAGE`), never invented by the LLM.
  - `ignition` is generated by the backend as a minimal valid object.
- If `MCP_DEFAULT_MASTER_IMAGE` is not configured, `create_vm` is rejected
  **before** any MCP call with an explicit, human-readable error.

## Client abstraction

`MCPClient`: `connect()`, `listTools()`, `getToolSchema(name)`, `callTool(name, args)`,
`disconnect()`. Two implementations:
- `StdioMcpClient` — spawns the real server (`MCP_MODE=stdio`).
- `MockMcpClient` — in-process fake honoring the same schemas (`MCP_MODE=mock`),
  used for safe demos and tests. No real VMs are touched.
